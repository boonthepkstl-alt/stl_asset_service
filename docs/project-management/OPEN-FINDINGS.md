authoritative detail on any PRD-level question, follow the link back to
`RAISE-PRD.md` §16 — this file summarizes, it doesn't supersede.

**Maintenance rule:** add a finding when one surfaces during any checkpoint
(per [`PROJECT-CHECKPOINTS.md`](PROJECT-CHECKPOINTS.md)'s process). Mark
**Resolved** with the resolving PR/commit when closed — never delete a row,
so the history of what was once open stays visible.

The direct sibling of **F-35** (asset code generation scheme): same shape of question, opposite answer — for assets the company's format is *constructible*, so the open part is the missing code tables; for employees the format is *not* constructible by RAISE at all, so generation is out of scope by nature, not by lack of information | User Q&A, 2026-09-03; implemented in [PR #81](https://github.com/boonthepkstl-alt/stl_asset_service/pull/81) (`CHECKPOINT-2026-09-03-006`) | Open — **not blocked**: the confirmed scope (validate the format on input only, deliberately *not* auto-generate) is **already shipped** — Create Employee rejects anything that isn't exactly 8 digits, on blur and on submit, with format checked before uniqueness. **What remains open** is a genuine follow-up: **seed fixtures and the backend auto-generation fallback still emit the legacy `EMP-####`/`EMP-<hex>` form, which the app's own new format check rejects** — so RAISE currently enforces a convention its own generated data does not follow.
